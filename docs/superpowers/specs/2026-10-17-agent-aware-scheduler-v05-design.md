# v0.5.0 Agent-aware Scheduler 缺口收敛与受控启用设计

## 状态

待用户审阅。本文基于 v0.4.9 正式发布后的 `main` 状态，定义下一阶段的范围；本文获批后再编写逐任务实施计划。

## 背景与当前事实

- v0.4.9 已正式发布，Server schema v19、Worker schema v6。
- Worker readiness contract、Server 校验与解释性证据，以及 `readiness-v1` 确定性软评分已由 PR #141 合入；配置 `prepared_workspace_score_enabled` 默认关闭。
- 现有评分只影响硬过滤后的合格 Worker，使用 Runtime/Environment warmth、Repository affinity、准备成本和容量余量四类信号。缺失、过期或非法信号不能取得正向分；关闭评分时沿用 least-active 与既有平分轮换。
- 现有实现的 CI/fixture 证据不证明真实 Worker 分布、任务时延或生产收益。v0.4.9 尚有双 Worker 升级恢复、真实 Provider、OCI/egress、安全证书、公网源站、NAT Relay、缓存性能和供应商账单边界等独立目标环境验收项。
- README 与 v0.4.9 发布台账已更新，但长期路线图仍保留 v0.4.8 基线；readiness 状态、并行开发计划和原评分设计/实施计划也保留“本地实现/等待 CI 或用户审阅”等过期陈述。下一阶段先校正事实来源，不能据旧文档重复实现已合并的评分能力。

## 目标

将 v0.5.0 限定为 Agent-aware Scheduler 的缺口核查和安全受控启用阶段：先确认现有硬约束覆盖情况，再只补齐经证据确认的缺口；保持 readiness 软评分默认关闭，完成可回退的受控验证后再决定是否建议启用。

## 非目标

- 不重写 PR #141 已合入的 `readiness-v1` 评分器。
- 不将 v0.4.9 的真实 Provider、生产网络、双 Worker 和供应商账单验收隐去或合并成 CI 结果；这些验收在实现收敛后单独执行。
- 不把 Mobile pairing/push、Execution Usage MVP、Private Worker Pool、跨节点 Artifact 或 Relay 生产化并入 v0.5.0。
- 不引入通用 Workflow Engine、LLM Gateway、AI Execution OS、Model Serving Platform 或 GPU Cloud 能力。
- 不在本规格中预先批准数据库 schema、公共 wire contract 或不兼容配置变更；若缺口核查发现必须变更，先提交独立合同/迁移设计供审阅。

## 设计决策

### 1. 先核实缺口，再限定实现

实施计划先对照 Agent-aware 长期路线图和当前调度代码，形成“硬约束 → 权威数据 → 过滤点 → 当前测试/证据 → 缺口”矩阵。核查至少覆盖 Runtime/Tool capability、项目与凭据授权、Environment/隔离、Worker pool、并发/容量和资源约束。只把无法由现有实现或证据满足的项列为代码任务；已经满足的项只补状态链接，不重复实现。

所有安全、权限、能力和容量硬约束必须在软评分之前执行。软评分不能让不合格 Worker 进入候选，也不能削弱租户、项目或凭据边界。

### 2. 复用现有确定性软评分

保留评分版本 `readiness-v1`、现有四因素与权重、固定快照和稳定排序语义。缺失/过期 readiness 按 unknown 处理；候选顺序变化不得改变决策；仅成功创建 Attempt 后推进既有平分轮换。任何改变公式、信号字段、有效期或排序优先级的工作均须单独提出设计，不作为隐式“调优”。

### 3. 保守的启用与回退

`prepared_workspace_score_enabled` 在默认配置、旧配置和 v0.5.0 Release 中继续为 `false`。不增加任务级覆盖、自动启用或通过真实环境变量推断模式的行为。受控环境显式开启后，若配置无效、评分证据缺失或出现异常，操作人员可关闭开关恢复 least-active + 既有轮换；不能静默放宽硬过滤。

### 4. 证据和隐私

复用当前有界 scheduler decision evidence，记录评分开关/版本、候选分项、unknown/stale 类别、选中/回退理由。解释不得泄漏其他项目仓库/模板、凭据、提示词、绝对路径或不相关 Worker 数据。若核查发现 evidence 不足，只能增加有界且向后兼容的观测字段；不新增持久执行事实源。

## 验收与启用门槛

### 自动化实现门槛

- 默认关闭、旧配置、关闭开关时与现有 least-active + rotation 行为一致。
- 硬约束优先；凭据、项目、安全、Runtime、环境、Worker pool、并发或资源不合格者不受分数影响。
- 相同快照和输入顺序变换下决策确定；stale/unknown 不获正分；候选/evidence 有界且项目隔离。
- 评分开启和关闭均有公平性及调度开销回归；不在没有可靠基线时设绝对时延目标。
- 配置回退、旧 Worker 兼容、重启和 Attempt 创建边界覆盖完整 CI。

### 后置目标环境门槛

功能和 CI 收敛后，在受控环境的两个独立 Worker 上进行关闭评分基线与显式开启对照。开始前冻结 workload、采样方法和通过阈值；至少记录 Worker 选择分布、公平性、冷/热准备时延、完整 Job 时延、失败/重试和调度开销。出现持续 Worker 垄断、结果退化或证据不可解释时，保持默认关闭并回退。

该对照只验证 Scheduler 的适用性，不替代 v0.4.9 的 Provider、升级恢复、安全、NAT Relay、供应商账单和缓存生产验收；单次对照也不能宣称通用性能提升。

## 分阶段交付

1. **状态核对：** 校正 README、长期路线图、P0–P2 台账和 readiness 状态，明确 v0.4.9、PR #141、评分默认值及环境验收的分别状态。
2. **调度缺口矩阵：** 盘点硬过滤、评分、兼容、解释和测试。输出唯一的最小代码清单；若无已证实代码缺口，不为凑版本添加实现。
3. **经核准的实现切片：** 按矩阵为每项缺口独立更新合同、实现、回归和操作说明；跨 schema/wire contract 的事项先停在独立设计审阅。若核查未发现可交付的用户价值缺口，不为发布而制造代码变化或空版本，应重新确定下一个交付主题。
4. **自动化收尾：** 在实现切片完成后运行定向、全量、race、vet、漏洞扫描及相关 CI；验证评分默认关闭和回退行为。
5. **后置受控验收：** 执行双 Worker 对照，生成脱敏证据；由结果决定是否仅建议在受控部署中启用，不自动更改发行版默认值。

## 发布边界

v0.5.0 可以按已确认的 CI 发布门槛独立发布，但 Release Notes 必须说明评分仍默认关闭及目标环境验收状态。只有后置对照证据通过，才可建议受控部署显式启用；不得由 CI/fixture 宣称真实 Worker 或公网生产已验收。

## 自审

- **重复实现：** 明确 PR #141 已实现 readiness-v1；计划必须先做差距核查，不能从零重建评分。
- **范围：** Usage、Mobile、Private Worker Pool、跨节点 Artifact、Relay 运营和 v0.4.9 目标环境验收均被分离，避免多子系统合并成一个版本目标。
- **兼容与安全：** 固定默认关闭、硬过滤先行、unknown 不加分、旧路径可回退；未获批的 schema/wire 变更被排除。
- **验收可信度：** 明确区分 CI/fixture 与目标环境对照，要求对照前冻结方法和阈值，不把模拟数据冒充生产收益。
- **文档事实：** 记录长期路线图的 v0.4.8 状态漂移，并要求以 v0.4.9 Release Status 和当前主线实现为准。
