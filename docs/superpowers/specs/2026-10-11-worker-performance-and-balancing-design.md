# Worker 性能与调度均衡设计

## 问题

近期本地运行暴露出几项会降低分布式执行价值的问题：当多个 Worker 的活跃任务数相同时，符合条件的任务可能连续落到 Worker A；简短提示也可能携带很长的历史上下文进入 Runtime。另有一次任务结果显示 `bwrap` 命名空间错误，但任务状态为成功。现有 Runtime 完成检查已经验证进程退出码和 Runtime 最终成功信号；在取得原始 Runtime 事件前，不能贸然改变成功判定。

已保存的若干成功任务指标显示，Runtime 墙钟耗时约为 6.5～13.7 秒，进程峰值 RSS 约为 313～333 MiB。这些数据不是端到端耗时，也不能单独说明编排架构带来了多少额外开销。要计算架构损耗，需要相同任务的本机直跑基线和分阶段耗时。

## 目标

- 在不放宽在线状态、能力、模板、凭据、项目和槽位限制的前提下，让等负载的合格 Worker 轮流接收任务。
- 观测请求字节数和各阶段耗时，从而区分上下文成本与编排成本。
- 通过结构化 Runtime 证据识别执行失败，避免把失败记为成功。
- 建立可复现的单 Worker、双 Worker、冷工作区和热工作区性能基线。

## 非目标

- 不静默截断、总结或删除对话历史和附件。上下文由调用方决定；服务端报告请求大小，并在超过配置上限时返回可操作的错误。
- 本次不增加由调用方任意指定 Worker 的能力。
- 不仅凭 stdout 或 Agent 回答中出现 `bwrap` 等字样改变 Runtime 成功状态。
- 在获得可比的基准数据前，不宣称已经提升性能。

## 设计

### 调度并列负载公平性

保留现有资格过滤和“优先选择活跃任务最少 Worker”的规则。若多个合格 Worker 的活跃数并列最低，按 Worker ID 排序，并使用 Server 自有游标在并列集合中轮换。只有成功分配后才前移游标；不能再由 Peer 到达顺序决定赢家。轮换不得绕过在线状态、能力、模板、凭据、项目和槽位检查。调度观测继续记录候选者和最终选择。Server 重启后游标不保证保留；该功能改善公平性，不提供持久 Worker 亲和性。

### 请求和阶段观测

记录请求体字节数，以及现有生命周期边界的时间戳：接收、入队、分配、Runtime 启动、Runtime 结束、结果持久化。通过现有追踪/指标路径暴露有界数值，不记录请求正文、凭据或附件内容。保留配置的请求大小上限；超过上限时返回可操作的 `REQUEST_TOO_LARGE` 错误，并提供配置上限，不回显请求正文。不得通过提高默认上限来掩盖上下文过量。

### Runtime 完成状态诊断

改变完成状态逻辑前，先取得并检查该次运行的结构化事件、进程退出状态、协议状态和清理状态。针对已确认的失败原因添加回归测试。只有满足现有成功条件（进程退出码为零、Runtime 最终事件报告成功、没有协议错误、清理已确认）时任务才能成功。若这些条件成立但工具仍报告沙箱错误，应通过结构化 Runtime 状态或验收验证暴露工具失败；绝不能从最终回答中的任意文本推断失败。

### 性能基准

添加可重复的基准/证据脚本，在提示、Runtime、模型和工作区相同的条件下比较：

1. 本机直接运行 Runtime（基线）；
2. 经由单个 Worker 执行；
3. 两个合格 Worker 在并发负载下执行；
4. 冷启动与热 Prepared Workspace 执行。

报告端到端 P50/P95、阶段耗时、成功率、请求字节数、可用时的输入/输出/缓存 Token，以及每个 Worker 的峰值 RSS。记录样本数和环境信息。首次运行只作诊断，不增加脆弱的绝对耗时 CI 门槛。CI 检查基准脚本契约和结果格式；性能结论根据重复运行的本机或专用 Runner 数据得出。

## 失败处理与兼容性

- Worker 在分配时变为过期或不合格，调度器只从剩余合格集合中选择。
- 没有合格 Worker 时，保留当前阻塞原因行为。
- 请求超过配置上限时，在持久化前拒绝，并在稳定错误字段中提供上限值。
- Runtime 证据不完整或清理未确认时，依照现有生命周期规则将任务保持为失败或未决状态。
- 新增观测字段必须是向后兼容的，且不得暴露机密信息。

## 验证

- 单元测试验证等负载轮换，并验证资格与容量过滤优先于轮换。
- HTTP 测试验证请求过大时会返回配置上限，且不会回显请求正文。
- Runtime 回归测试重现已确认的 `bwrap` 故障路径，并区分结构化工具失败与普通文本提及 `bwrap`。
- 基准契约测试验证字段、样本统计和单/双 Worker 场景输出。
- 运行相关 Go 包测试和仓库要求的 CI Gate。

## 实施顺序

1. 根据原始 Runtime 证据确认 `bwrap` 结果，并为已验证原因补回归测试。
2. 添加调度并列负载轮换及专项测试。
3. 增加请求大小和生命周期观测。
4. 增加基准工具并采集可比数据。
5. 根据实测结果更新实施文档和剩余限制。
