# v0.4.7 Container and Trigger/Delivery acceptance

This procedure closes `ECO-03 / INT-01` only on the target Docker/OCI host and
through an authenticated service identity on trusted CI. The resulting
`dist/v0.4.7-acceptance/integration-report.json` must pass
`scripts/validate_v047_integration_results.py`.

Existing CI Environment tests use the built-in `process` provider. Their report
now labels the v0.4.7 fields as fixture-only and ineligible for this real-host
Gate. Likewise, one `ci_trigger_delivery.py` record supplies bounded source,
result, and Artifact facts but cannot by itself prove the complete duplicate,
failure, and retry matrix.

## Fixed cases

| ID | Required real-environment observation |
| --- | --- |
| ENV01 | The registered `container` provider creates the Attempt container; host CLI execution is false. |
| ENV02 | A deliberate file escape attempt outside the Attempt workspace is blocked. |
| ENV03 | A deliberate network escape against the deployment's denied destination is blocked. |
| ENV04 | The Attempt container crashes, the controller restarts, and the run is not replayed. |
| ENV05 | Release confirms both Runtime and Environment cleanup and no residual container remains. |
| INT01 | An authenticated CI service identity submits the pinned Job and the Server accepts it. |
| INT02 | Repeating the same delivery uses the same submission key and Job ID and creates one side effect. |
| INT03 | A failed Job produces a bounded failed-delivery record without raw upstream output. |
| INT04 | A bounded retry preserves source/spec/result/manifest and final Artifact provenance. |

Every case records the exact candidate SHA. ENV cases also record a unique
Attempt ID and the deployed immutable image digest. INT cases record a delivery
ID, Job ID, and SHA-256 values for the submission key and Job spec. INT03 also
requires the failed result hash; INT04 requires result and manifest hashes plus
the Artifact provenance check. The report stores no client config, service
identity value, bearer header, credential reference, prompt, or raw result
text.

## Target-host procedure

1. Build the exact candidate and deploy its Container Environment controller by
   immutable `sha256` digest. Record the identical build and candidate SHA.
2. Run ENV01 on the target Docker/OCI host. Inspect the container identity and
   ensure the Worker did not fall back to its host CLI.
3. Run ENV02 with a harmless sentinel outside the mounted Attempt workspace;
   prove it cannot be read or changed. Run ENV03 against a dedicated denied
   test endpoint; do not probe unrelated networks.
4. For ENV04, terminate the Attempt container and restart the controller. Prove
   the durable marker prevents replay. For ENV05, invoke Release and inspect
   Docker to prove the owned container is absent; `UNKNOWN` is a failure.

## Trusted-CI procedure

1. Provision the service identity through the existing private client config on
   the trusted runner. Do not pass credentials as command arguments or copy the
   config into an artifact.
2. Run `ci_trigger_delivery.py` with a stable delivery ID, full candidate SHA,
   and frozen Job spec. Retain the mode-0600 delivery record.
3. Repeat the same logical delivery and verify the record reports the existing
   Job. Query the Server to prove the logical delivery created one side effect.
4. Run one Job that terminates as failed and retain its bounded `JOB_FAILED`
   record. Exercise one bounded transport retry and verify all recorded hashes
   and final Artifact references against the Server.
5. Assemble the nine sanitized case results, set `status` to `PASSED` only when
   every observation is true, and run:

```sh
python3 scripts/validate_v047_integration_results.py \
  dist/v0.4.7-acceptance/integration-report.json
```

The validator rejects fixture execution, a mutable or drifted image, host CLI
substitution, missing file/network negatives, incomplete cleanup, missing
crash/restart, unauthenticated ingress, duplicate side effects, missing failed
delivery, incomplete provenance, failed/absent cases, and credential-shaped
data. Keep the tracker `BLOCKED_ENV` until the sanitized report and underlying
restricted logs have been reviewed.
