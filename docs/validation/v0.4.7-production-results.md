# v0.4.7 independent-host production acceptance

`VAL-01` requires one Server record, two independently identified Linux Worker
records, real Codex/Claude/MCP execution, controlled faults, a task lasting at
least 24 hours, capacity evidence, and an operational v13 to v16
upgrade/restore rehearsal. CI simulation cannot close this Gate.

Collect and verify the three host records with
[`dual_host_preflight.py`](dual-host-preflight.md). Its
`v047_production_hosts` output is the sanitized `hosts` input for
`dist/v0.4.7-acceptance/production-report.json`. Each Worker must have a unique
machine-id hash plus Codex, Claude, MCP, computecloud binary and candidate SHA
records.

## Fixed cases

| ID | Required observation |
| --- | --- |
| VAL01 | Preflight verifies one Server and two independent Worker machine IDs. |
| VAL02 | A real Codex run retains its native final and Task/Attempt provenance. |
| VAL03 | A real Claude run retains its native final and Task/Attempt provenance. |
| VAL04 | A real MCP call retains the pinned MCP version and result provenance. |
| VAL05 | One MapReduce-style Job executes Tasks on both Worker IDs and completes once. |
| VAL06 | Worker SIGKILL is timestamped, reconciled, and creates no duplicate Attempt. |
| VAL07 | Server SIGKILL is timestamped and recovers without committed-state loss. |
| VAL08 | Network loss/recovery is timestamped and preserves the confirmed event watermark. |
| VAL09 | One task runs at least 86,400 seconds with continuous lease and event evidence. |
| VAL10 | Artifact access control and every retained Artifact hash are verified. |
| VAL11 | The declared capacity matrix completes with zero failures and SQLite integrity `ok`. |
| VAL12 | A real v13 snapshot upgrades to v16, while rollback restores the untouched v13 snapshot. |

All cases retain nonempty Task and Attempt IDs. VAL06–VAL08 retain fault and
recovery timestamps. The report's correctness counters for duplicate Attempts,
accepted stale generations, invalid Artifacts, lost confirmed events, terminal
state regressions, and unauthorized access must all be zero.

## Upgrade and rollback evidence

1. Stop the v13 Server using the operating procedure and create its immutable
   snapshot. Record its SHA-256, `user_version=13`, v13 binary hash, integrity
   result, Job counts, and Artifact hashes.
2. Clone the snapshot and start the exact v0.4.7 candidate on the clone. Record
   `user_version=16`, `PRAGMA integrity_check=ok`, candidate binary hash, counts,
   and Artifact hashes.
3. Exercise representative read and new-write paths on the migrated clone.
4. For rollback, stop the candidate and restore the original untouched v13
   snapshot into an isolated directory. Start the v13 binary and record
   `user_version=13`, integrity `ok`, counts, and Artifact hashes.
5. Set `rollback_method` to `restore_snapshot` and
   `manual_user_version_change` to false. Editing `PRAGMA user_version`, schema
   tables, or migrated files is an automatic failure.

## Validation

Keep credentials, prompts, native output, and user repositories outside the
sanitized report. Preserve restricted logs separately and retain only IDs,
versions, hashes, timestamps, counters, and bounded booleans in JSON. Run:

```sh
python3 scripts/validate_v047_production_results.py \
  dist/v0.4.7-acceptance/production-report.json
```

The row remains `BLOCKED_ENV` until this command passes on the assembled real
report and the underlying evidence receives review. Failed and interrupted
runs remain visible; do not replace them with local fixtures.
