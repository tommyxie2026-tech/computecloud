# v0.3.5 Fair Scheduling 运行与调优

- 目标版本：v0.3.5
- 基线：v0.3.4
- ADR：[ADR-011](../adr/0011-fair-scheduling.md)

## 1. 配置

~~~yaml
server:
  max_project_tasks: 8
  credentials:
    account-a: 2
  jobs:
    scheduler_aging_seconds: 300
    max_queued_tasks: 4096
    max_queued_tasks_per_project: 1024
~~~

max_project_tasks 是一个 Project 同时 active Attempt 上限；credentials.<ref> 是一个 Credential 同时 active Attempt 上限；scheduler_aging_seconds 是排队多久获得 1 个 effective-priority boost；两个 max_queued 字段控制 external admission。

## 2. Effective priority

~~~text
effective = min(10, base + floor(queue_age / aging_interval))
~~~

例如 aging=300s：base=8/age=0m -> 8；age=5m -> 9；age=10m -> 10。Aging 不修改数据库里的 base priority。

## 3. Fairness

同 effective priority 内执行 Project round-robin；Project 内再做 Job/group round-robin。Standalone Task 自身作为 group。Scheduler cursor 是内存优化，Server 重启后顺序可以重新开始，但 Task durability 不受影响。

## 4. Backpressure

新提交可能返回 QUEUE_BACKPRESSURE_GLOBAL 或 QUEUE_BACKPRESSURE_PROJECT。调用方应降低提交速率，不要无界立即重试。

同一个 idempotency key 对已经接受的请求仍可安全 replay，即使此时队列已满。Internal Reduce Stage 是已接受 Job 的一部分，不使用 external admission gate。

## 5. Scheduling blocker

Job scheduling_blockers 可能包含：

~~~text
JOB_CAPACITY_EXHAUSTED
PROJECT_CONCURRENCY_EXHAUSTED
CREDENTIAL_CONCURRENCY_EXHAUSTED
WORKER_CAPACITY_EXHAUSTED
NO_READY_WORKER
TEMPLATE_OR_CAPABILITY_MISMATCH
RETRY_BACKOFF
~~~

排查顺序：先看 Retry/backoff/deadline，再看 Credential/Project/Job concurrency，再看 Worker slot，最后看 Runtime/template/capability。

## 6. 调优原则

不要把 queue limit 当吞吐调节器。吞吐优先通过 Worker slots、Project/credential concurrency 和真实 Runtime 容量决定。

Aging interval 太短会弱化 priority；太长会增加低优先级 starvation 时间。默认 300s 是保守起点，需要根据真实 Job 时长重新测量。

## 7. 回退

v0.3.5 没有数据库 schema migration。回退到 v0.3.4 时，需要从旧版本严格 YAML 配置中移除新增 scheduler 字段；durable Job/Task/Attempt 数据兼容；in-memory fair cursor 自然丢弃。

## 8. 边界

v0.3.5 不提供 preemption、weighted fair share、DRF、CPU/GPU placement、Workspace affinity 或 Agent-aware score。这些属于后续 Scheduler 演进。
