## 2. 交付顺序

| 阶段 | 依赖 | 工作项 | 通过标准 | 状态 |
| --- | --- | --- | --- | --- |
| M1 基础契约 | 设计 | 公用应用服务；显式数据库迁移；Job 类型/Schema；权限范围；锁定 MCP Go SDK 版本 | 旧 gRPC 回归通过；v1→v2 迁移与备份恢复通过；旧二进制拒绝新库 | 待实施 |
| M2 single Job | M1 | HTTP 接受/查询/取消/事件/结果；Job CLI；静态 Token | 相同提交只产生一个 Job/Task，取消与成功竞态确定，重启不丢状态 | 待实施 |
| M3 MCP | M2 | 四个工具、Streamable HTTP、结构化结果、Origin/版本校验 | 固定真实 Codex 可提交并轮询 single；网络重试不重建任务 | 待实施 |
| M4 Map 与公平调度 | M2 | 显式分片事务、Job 并发、轮转、deadline、取消扇出 | 多 Worker 并行执行；单个 Job 不吃满同级队列；额度和期限一致 | 待实施 |
| M5 Reduce 交接 | M4 | 冻结清单/唯一屏障；Worker 输入下载授权；报告合并；补丁合并和验收 | 屏障前后崩溃不产生重复 Reduce；坏产物/越权下载/冲突均明确失败 | 待实施 |

这些是实现和验收配置，不阻塞本设计成立：目标 Linux 发行版/架构、真实 Codex/Claude 版本、允许模型、账号/上游类型、仓库引用、TLS 域名、策略及验收命令。版本未知时先使用 fixture 开发，不能伪造真实兼容性结论。

## 3. 验收矩阵

| 编号 | 场景/故障注入 | 预期与必要证据 |
| --- | --- | --- |
| V01 | 同键同参、异参、提交响应丢失；接受后默认配置变化 | 原 Job ID 不变；异参 409；不重复展开分片；保存原解析规格 |
| V02 | JSON 重复成员、未知字段、坏路径、分片同 key、超出限制 | 接受前拒绝；无残留 Job/Task |
| V03 | owner/project 越权、Token 混用 | 不能读取/取消/下载他人对象；Worker/模型 Token 不能提交 Job |
| V04 | single 兼容与独立旧 Task | 两类入口均可用；子 Task 不能绕过 Job 单独取消 |
| V05 | 两 Job、受限账号、不同 Worker 槽位并发 | 所有上限均不超限，同级 Job 轮转可观察 |
| V06 | 新 Job 指派旧 Worker；模板摘要不一致 | 不派发或明确失败，不静默忽略新 Assignment 字段 |
| V07 | Map 成功/失败混合 | 必要 Map 全成功才有 Reduce；失败停止其余任务，部分产物可诊断 |
| V08 | 屏障事务前、提交后、下发前杀 Server | 相同 Reduce Task ID；唯一清单摘要；无重复启动命令效果 |
| V09 | 取消与最后一个 Map/Reduce 完成并发；取消扇出中重启 | 停止意图/成功提交按事务顺序决定；恢复继续停止；无悬挂新任务 |
| V10 | Worker 断线、SIGKILL、失联超过租约 | 本地执行停止；不确定清理时 Job 非终态且额度保留；不重派 |
| V11 | 队列耗尽期限、Reduce 排队耗尽期限 | 全链路共享原 deadline，不重置超时 |
| V12 | 上传/完成 ACK 丢失、相同/不同 final_hash 重传 | 同结果可确认，冲突结果拒绝；清单只引用有效结果 |
| V13 | Reduce 输入跨 Job/越权、坏 hash、缺文件、压缩炸弹/路径穿越 | 不能下载或明确失败；无额外执行，不替换输入 |
| V14 | 报告跨模型汇总 | 结构有效，证据来源可追溯；保存模型/版本和模板摘要 |
| V15 | 独立文件补丁、重叠路径、rename/symlink/submodule、测试失败 | 合法补丁合并；其他按策略拒绝；不以自然语言代替测试 |
| V16 | 事件分页、慢轮询、MCP 调用取消/断开 | 序号连续可续取；任务不被意外取消；返回体有界 |
| V17 | MCP Origin、版本、initialize、通知与合法工具错误 | 协议行为和错误分类正确，权限每次检查 |
| V18 | G1 文本、多轮工具、自定义工具、SSE、推理与 compaction | 原调用方执行工具，call ID/上下文保真；固定真实 Codex 完成任务 |
| V19 | G1 上游 401/429/5xx、半流断线、下游断开、超大事件 | 不自动重放或换账号；保留错误/中断，内存有界 |
| V20 | G1 Attempt 结束/取消/租约过期，伪造归属头 | 拒绝继续推理；归属由凭据推导；不允许提交 Job 或递归派发 |
| V21 | G1 正常、失败、未知用量、重启未结算记录、CLI 重复汇总 | 全部真实请求计入；不重复统计、不填伪零；unknown 可观察 |
| V22 | 迁移失败、备份还原、旧二进制、新旧 Worker、SQLite busy/磁盘满 | 不损坏原库；版本有界；不假接受；恢复步骤有证据 |

R1 增补：多代 Attempt 唯一活跃约束、在途旧上传、迟到 renew/events/complete、重试耗尽、剩余期限不足、取消后退避任务、不可重放模板拒绝、历史用量保留。R1 未实现前，max_attempts_per_task>1 必须拒绝。

## 4. 端到端演示与性能记录

演示 A：将 computecloud 固定 commit 的鉴权、调度、恢复分成 Map，使用两节点两个运行时生成 findings，Reduce 输出带来源的报告。演示 B：修改两个互不重叠的文件，Reduce 合并并运行受信测试；再注入冲突以验证失败行为。

每个演示保存 JobSpec、Job/Task/Attempt ID、Worker/CLI 版本、事件页、产物 SHA-256、验收退出码和发生故障的时间。真实模型测试须与 fixture 记录分开，不能用本机双进程冒充跨主机验证。

先用 fixture 测量 1/2/4/8 个 Worker、每节点 1/2/4 个 slots，报告实际 CPU/RSS、队列延迟、SQLite 写延迟/WAL 增长、事件与产物吞吐，再选目标环境配置。这些是测试维度，不是承诺支持的节点上限。模型耗时与数据库调度耗时分开统计，避免把供应商延迟归因于 Scheduler。
