# v0.4.x closeout plan

Baseline: `main` at `7f9de5da881fc6c203fc44380144cd49fa56515a` (2026-10-07).
Stable release: `v0.4.6`. `v0.4.7-rc.1` is a scoped prerelease and does not
contain every later `main` change. The product remains an Agent-aware
Distributed Job Execution Platform / Agent Job Executor.

This plan tracks implementation, automated checks, real-environment acceptance,
and release separately. The old v0.4.7–v0.4.10 release slots in the
[follow-up plan](v0.4.5-follow-up-release-plan.md) are historical. Freeze a new
candidate tag only after its scope and evidence are known; do not infer a number
of remaining releases from those slots.

## Execution rules

1. Each code slice follows contract/migration review, implementation, focused
   tests, full `main` CI, and an updated evidence record. Keep unrelated slices
   in separate PRs. A fixture PASS never closes a real-host acceptance row.
2. VAL-01 starts with the [multi-node cases](../validation/multi-node-poc.md)
   and [dual-host preflight](../validation/dual-host-preflight.md). If Server
   shares one Worker host, disclose that topology and do not claim independent
   Server isolation or capacity.
3. Goal automatic Re-plan and production Relay remain disabled/unclaimed until
   their own end-to-end gates pass. Preserve direct transport and existing Job,
   Task, Attempt, Artifact and Worker ownership semantics.
4. Release readiness requires no open critical correctness failures, a passing
   full CI on the exact candidate SHA, complete upgrade/rollback evidence, and
   explicit known limitations. The release manager records each row as DONE,
   PARTIAL, BLOCKED or DEFERRED and freezes scope before choosing a stable tag.

The Linux preflight collector is available ahead of the final validation phase.
It creates reviewable host identity and version records without collecting
credentials; it does not certify a deployment or replace the actual test results.
