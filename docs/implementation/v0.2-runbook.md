# v0.2 运行与升级指南

日期：2026-09-22。v0.2 已实现 Job HTTP/MCP、显式 Map/Reduce 和默认关闭的 Responses 网关。保持单 Go 二进制、单活动 Server、各节点本机 SQLite，无额外数据库或消息队列服务。当前自动验证使用协议 fixture，真实 Codex/Claude、上游模型和独立双机仍需按[验证记录](../validation/v0.2-results.md)验收。

## 1. 构建与验证

需要受信 Linux 节点、Go 1.26+、Git；烟测需要 Python 3.12+。本次工具链为 Go 1.27.1，MCP 使用官方 Go SDK v1.8.0。

```sh
make build
./bin/computecloud version
make vet test race smoke
```

`make smoke` 会启动真实 Server/Worker 进程，使用模拟 CLI，覆盖旧 Task 与新 Job 命令、取消、SIGKILL、租约停止和备份。不会调用模型账号。另可用 `python3 scripts/smoke.py --binary bin/computecloud --old-binary /path/to/v0.1/computecloud` 验证旧程序拒绝新数据库。

`make capacity-check` 执行容量工具自测及小矩阵；`make capacity` 执行 1/2/4/8 Worker × 1/2/4 slots 的本机 fixture 矩阵并输出 JSON。指标定义、完整命令及真实部署门槛见[容量与部署验收](../validation/capacity.md)。不会调用真实模型，不能替代跨主机测试。

## 2. 开启 Job 与 MCP

沿用 [v0.1 运行指南](v0.1-runbook.md) 的 Worker、仓库白名单、凭据、策略和验收命令配置。先固定真实 CLI 版本输出与模型 ID；所有参与同一执行模板的节点必须配置相同策略和验收 argv。

1. 在 Worker 配置中添加并审阅所需策略与验收模板。报告 Map、报告 Reduce 和补丁 Reduce 使用只读策略；补丁 Map 使用可写策略。代码验收配置真实测试命令，报告任务可用空命令数组，报告结构与证据由 Worker 另外验证。
2. 执行 `computecloud templates --config worker.yaml`，将输出中的 `templates` 数组配置到 `server.jobs.templates`。该命令只计算已配置内容的摘要，真正 Worker 启动还会探测 CLI 版本。不要从未经审阅的远端注册信息自动接受摘要。
3. 在原 Server 配置加入下列段，并给调用方显式授权 Job scopes。

```yaml
server:
  # 此为增量段；保留原 listen、data_dir、tls、workers、credentials 等字段。
  http:
    listen: 127.0.0.1:7444
    allowed_origins: []
  jobs:
    enabled: true
    templates: [] # 替换为上一步审阅后的数组；空数组不能接受任何执行模板。
  mcp:
    enabled: true
    path: /mcp
```

本机可沿用 `tls.insecure_loopback: true`；远程必须配 TLS，HTTP 与 gRPC 共用证书配置。默认 Job 限制为 32 个分片、8 并行、建议 2 并行、每 Task 1 次 Attempt，输入总包限制 128 MiB；可降低配置限制。

调用方身份示例：

```yaml
scopes: [jobs:submit, jobs:read, jobs:cancel, tasks:submit, tasks:read, tasks:cancel]
```

未填写 scopes 的旧用户保留旧 Task 权限，不自动获得 Job 或模型权限。只使用 Job 时可去掉 tasks 三项。模型调用方使用单独的 `models:invoke` Token，Worker 使用独立节点 Token。

客户端配置增加：

```yaml
client:
  address: 127.0.0.1:7443
  http_url: http://127.0.0.1:7444
  token_file: ../secrets/user.token
  tls:
    insecure_loopback: true
```

配置文件的相对文件路径仍相对于配置文件所在目录。

## 3. 投递、跟踪与下载

修改 [single 示例](../examples/v0.2/job-single.json) 或 [Map/Reduce 示例](../examples/v0.2/job-map-reduce.json)，填写实际项目、仓库引用、完整 commit、模型、凭据、策略和验收引用。不要使用浮动分支或任意远程 Git URL。

```sh
./bin/computecloud job capabilities --config client.yaml
./bin/computecloud job submit --config client.yaml --key review-001 --file job.json
./bin/computecloud job get --config client.yaml --id JOB_ID
./bin/computecloud job watch --config client.yaml --id JOB_ID --after 0
./bin/computecloud job tasks --config client.yaml --id JOB_ID --limit 50
./bin/computecloud job result --config client.yaml --id JOB_ID
./bin/computecloud job artifacts --config client.yaml --id JOB_ID
./bin/computecloud job download --config client.yaml --id JOB_ID --artifact ARTIFACT_ID --out result.tar
./bin/computecloud job cancel --config client.yaml --id JOB_ID --control-id cancel-001
```

提交失败重试时复用 `--key`；同键异参返回冲突。`job events --after SEQ --limit N` 支持单次取事件；`tasks/artifacts --cursor ID` 取下一页。下载拒绝覆盖已有文件，并核对 Server 提供的 SHA-256。停止 watch 或断开 MCP 只停止观察；取消执行须调用 cancel。

Server 先事务保存 Job 与初始 Task，再返回 Job ID。Worker 按能力、模板摘要与并发额度获取命令，在独立 Git 工作区运行。所有 Map 成功并确认清理后，Server 冻结获选产物清单并创建唯一 Reduce。Reduce 下载时逐次授权，启动 CLI 前校验大小、哈希和 tar 条目，再汇总报告或受信应用补丁。取消先保存停止意图，确认全部清理后才发布终态。

| 现象 | 处理 |
| --- | --- |
| `TEMPLATE_NOT_CONFIGURED` | 补充 Server 受信模板清单，核对请求引用 |
| `NO_READY_WORKER` / `TEMPLATE_OR_CAPABILITY_MISMATCH` | 核对在线节点、仓库、模型、策略、版本及模板摘要 |
| `CAPACITY_EXHAUSTED` / `JOB_CAPACITY_EXHAUSTED` | 等待节点、账号、项目或 Job 额度；额度包括尚未确认清理的执行 |
| `GATEWAY_ROUTE_CHANGED` | 已冻结 Job 的路由配置被改变；恢复原路由或取消后以新键提交 |
| `JOB_OUTPUT_INVALID` | 查看 Task 错误及结果包；模型最终 JSON、证据或修改范围不符合契约 |
| `JOB_INPUT_ERROR` / `PATCH_CONFLICT` | 检查冻结输入、哈希、包内容或补丁；不会跳过必要分片 |
| `RECONCILING` | Worker 清理尚未确认；恢复原节点/进程监管，不手改 released 或重新派发 |

报告包包含 `findings.json` 或 `review.json`、`review.md`；补丁 Map 增加 `changes.paths.json`，补丁 Reduce 增加 `merge-report.json`。均保留 `report.json`、`changes.patch`、`stderr.log`。报告证据路径/行号按原 commit 验证；格式和来源可核验，不代表模型的判断必然正确。

## 4. Codex MCP 接入

使用 [codex-mcp.toml](../examples/v0.2/codex-mcp.toml)，将 URL 改为 Server `/mcp`，通过 `COMPUTECLOUD_TASK_TOKEN` 提供 Job Token。四个工具为 `submit_job`、`get_job`、`cancel_job`、`get_result`，提交返回后按 `poll_after_ms` 轮询。

MCP 无持久 Session，不提供 GET 推送流。存在 Origin 时必须精确匹配 `allowed_origins`，无 Origin 的 CLI 请求可以使用。平台负责 HTTP 鉴权，工具每次再检查 scope 与对象归属。不要在后台 Worker 的 Codex 配置或环境中安装带任务提交凭据的 computecloud MCP；Worker 只需要节点身份及其执行凭据。

## 5. 可选 Responses 网关

首次接入应保持 `model_gateway.enabled: false`。启用时按 [Server 增量示例](../examples/v0.2/server-v0.2.yaml) 配置受信 HTTPS 上游、允许模型和上游 API Key 文件。必须使用该上游支持的合法 API 凭据；不从 CLI 登录文件导出秘密来假定 API 兼容。

- 静态模型 Token 的身份须配置 `scopes: [models:invoke]`、固定 `model_project` 与 `model_route`。本地 Codex 使用 [codex-gateway.toml](../examples/v0.2/codex-gateway.toml)；工具在本地运行，模型 API 不创建 Job。
- Worker 模式另配置 `credential_routes`、`public_base_url: https://HOST:7444/v1`。网关证书也须被 Codex 信任，gRPC 的 ca_file 不会自动改变 Codex 的证书信任库。Job 的 Codex credential_ref 匹配映射后，Server 固定路由并签发 Attempt 模型权限；Worker 自动用 CLI `-c` 参数设置 provider，用子进程环境注入 Token，不需要上游 Key，也不修改全局 Codex 配置。
- Claude 仍走原生运行时凭据，不能使用 Codex Responses 路由。`credential_routes` 不应映射给 Claude 使用的引用。
- 支持 `/v1/models`、`/v1/responses` JSON/SSE 和 `/v1/responses/compact`。仅内联文本、函数/自定义工具及推理/compaction 内容；媒体、托管工具、服务器对象引用、WebSocket、后台请求和 `store:true` 明确拒绝。
- `/responses` 补 `store:false`；compact 不补 store。嵌套工具、call ID 与不透明推理内容按 JSON 语义保留。网关不重试上游 POST，不换账号续接半截流。单 SSE 事件 4 MiB、非流响应 16 MiB；超限中断，不伪造成功。
- 并发准入在读取大请求前完成。默认总并发 16、路由 8、请求 16 MiB、流空闲 300 秒、请求 1800 秒。Attempt 状态每个新请求检查，并在在途请求中约每 500 毫秒重查；取消不能承诺供应商即时停止计费。

Server 数据库只保存模型 Token 摘要，持久 start 命令不保存原文；发送时从该 Attempt 的 256 位随机租约材料、ID、代次和专用域标签确定性派生，以便命令重放。传输及 Worker 私有执行日志包含原文，按租约秘密保护；执行结束后权限失效。上游 Key 始终留在 Server。

请求先记 `STARTED`，终结记 `COMPLETE/FAILED/UNKNOWN`；重启遗留请求转 `UNKNOWN`。缺失用量保持 NULL，不加上 CLI 汇总重复计数。Job 结果的执行内容不可变，`usage` 是独立用量记录的当前快照，可能在最后一个网关请求结算后完善。此计量不是严格费用预算或供应商账单对账。

## 6. 从 v0.1 升级与回退

1. 使用旧 Server 的维护模式停止新接收/分配；等待执行结束或取消，确认全部 Attempt 已释放。未确认清理的执行必须先处理。
2. 停止 Worker 与 Server。离线备份 Server；另备份各 Worker 数据目录。`computecloud backup` 在打开备份源时不迁移 schema。
3. 用 v0.2 启动 Server，事务执行 schema v1→v2→v3；存在未释放 Attempt 时拒绝升级。G1 关闭也创建用量表，不产生额外服务。Worker 数据版本升到 2，沿用原恢复逻辑。
4. 配置新 scopes 与模板后再开放 Job；旧 Task 接口继续可用。旧 Worker 只能处理符合原能力的独立 Task。
5. 回退时停止新程序，恢复完整升级前备份并使用旧二进制。旧 Server/Worker 均拒绝直接打开升级后的库；不要手改 user_version。

任务恢复不自动新建 Attempt。目录使用本机磁盘，禁止两 Server 同时写同一库，禁止通过共享网络文件系统做控制面 HA。结果及输入目录暂不自动清理；制定离线保留/备份策略，避免磁盘长期增长。

## 7. 构建产物与发布

本地可按 `Makefile` 中的版本构建 Linux amd64/arm64 发布包：

```sh
make release-package
cd dist/release
sha256sum -c SHA256SUMS
```

每个压缩包包含静态 `computecloud` 二进制、README、CHANGELOG，以及基础和 v0.2 示例配置。打包脚本只接受不带前导 `v` 的语义版本，目标文件已存在时拒绝覆盖；压缩包先在临时目录生成，通过 gzip/tar 完整性检查后才移入发布目录。二进制通过 `CGO_ENABLED=0`、`trimpath` 和版本 ldflags 构建。

GitHub Actions 在每次 `main` 分支 push 的完整验证通过后，生成名为 `computecloud-版本-dev.提交摘要` 的临时 artifact，保留 30 天。其他分支和 Pull Request 只运行验证，不产生可发布二进制。

正式发布需要先更新 `Makefile` 的 `VERSION` 并完成变更记录。推荐在最终发布提交中新增对应的版本化请求文件；例如 `release/v0.2.0.json`：

```json
{
  "schema_version": "release-request.v1",
  "version": "0.2.0"
}
```

请求文件名、内容版本和 `Makefile VERSION` 必须完全一致。该文件必须在触发发布的主分支提交中新增或修改；CI 完整验证通过后，以该提交创建标签和 GitHub Release。这使无法直接推送 Git 标签的自动化也能执行一次性正式发布。

也可在主分支 CI 通过后，手工创建指向同一提交的标签：

```sh
git tag -a v0.2.0 -m 'computecloud v0.2.0'
git push origin v0.2.0
```

标签必须为 `v` 加语义版本，并与该提交的 `Makefile VERSION` 完全一致。两种路径都会重新执行模块校验、静态检查、测试、race、烟测和容量小矩阵；成功后下载同一 workflow artifact，通过具备最小 `contents: write` 权限的独立 Job 创建 GitHub Release，附加 amd64/arm64 压缩包和 `SHA256SUMS`。预发布版本包含连字符，例如 `v0.3.0-rc.1`，生成的 Release 标记为 prerelease。已有同名 Release 时任务失败，不覆盖已发布资产；不要再次修改已发布版本的请求文件。
