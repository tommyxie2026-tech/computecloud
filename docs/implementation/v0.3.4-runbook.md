# v0.3.4 Long-running Job Reliability 运行与升级

- 目标版本：v0.3.4
- Server schema：v7
- Worker schema：v3
- ADR：[ADR-010](../adr/0010-long-running-job-reliability.md)

## 1. Liveness

长任务健康性以 Worker Renew 为准，而不是 Runtime stdout/stderr。

查看当前 Attempt：

~~~sql
SELECT id, task, generation, worker, last_renewed, lease_until, released
FROM attempts
WHERE released=0
ORDER BY last_renewed;
~~~

解释：

- `last_renewed` 持续变化：Worker/Attempt 控制通道仍活跃；
- Runtime 长时间没有 output，但 lease 正常：不是 hung 判据；
- `lease_until` 到期：Worker 不再拥有执行权，必须停止本地执行；
- Server 不可达时不会无限续租。

HTTP Job task projection 也返回 `last_renewed_ms / lease_until_ms`。

## 2. Deadline extension

HTTP：

~~~text
POST /v1/jobs/<job-id>/deadline
Authorization: Bearer ...
Content-Type: application/json

{
  "operation_id": "extend-20260927-01",
  "new_deadline_ms": "1790000000000"
}
~~~

需要身份 scope：

~~~text
jobs:extend
~~~

MCP 提供同义工具：

~~~text
extend_job_deadline
~~~

同 operation_id + 同 payload 可安全重试；同 operation_id + 不同 payload 会冲突。

配置：

~~~yaml
server:
  jobs:
    max_total_runtime_seconds: 604800
    max_deadline_extend_seconds: 86400
    max_task_events: 2000
~~~

Deadline extension 不会重置 Retry generation/budget，也不会改变 Artifact/Workspace ownership。

## 3. Deadline 与 Worker

Worker 不再把 Assignment 的 deadline 快照作为固定本地 timer。Server 是 mutable deadline 的事实源：

~~~text
deadline expired
    ↓
Server marks STOPPING/CANCELING
    ↓
stop command / lease invalidation
    ↓
Worker context cancel
    ↓
TERM -> KILL if needed
~~~

因此不要用修改 Worker 本地时间或 Assignment 文件的方式延长 Job。

## 4. Stop escalation

Worker 若需要停止仍在运行的 process group：

1. 发送 SIGTERM；
2. 等待 `stop_grace_ms`；
3. 若仍存活发送 SIGKILL；
4. 再次确认整个 process group 已退出。

若发生信号升级，Task event 中出现：

~~~text
attempt.stop_escalation
~~~

payload 含 `phase / term_sent / kill_sent / cleanup_confirmed`。

cleanup_confirmed=false 仍按现有 fail-closed 规则处理，不能自动把旧执行视作已消失。

## 5. Task event compaction

配置 `max_task_events` 控制每个 Task 保留的最近 event payload 数。

查看 floor：

~~~sql
SELECT id, seq, event_floor_seq
FROM tasks
ORDER BY updated DESC;
~~~

若客户端的 `after_seq` 早于 floor：

~~~text
EVENT_CURSOR_COMPACTED floor=N
~~~

处理方式：

1. 重新读取 Job/Task snapshot；
2. 接受 snapshot 为当前事实；
3. 从 floor 之后重新订阅。

不要把 compacted cursor 当作空事件响应。

`event_dedup` 保留 worker_seq/hash，因此 Worker 对已经压缩掉 payload 的旧事件重放仍可做 hash 一致性校验。

## 6. 升级 v0.3.3 -> v0.3.4

沿用 Server drain gate：

1. 停止接收新 Job；
2. 用旧版本把 active Attempts drain 到 0；
3. 停 Server；
4. 备份 Server data directory；
5. 部署 v0.3.4；
6. 启动并检查：

~~~sql
PRAGMA user_version;
PRAGMA integrity_check;
PRAGMA foreign_key_check;
~~~

预期 Server `user_version = 7`。

Worker schema 仍为 v3，不需要 Workspace schema migration。

## 7. 回退

v0.3.3 Server binary 不应直接打开 schema v7。

回退：

1. 停 v0.3.4；
2. 保存现场；
3. 恢复升级前 Server backup；
4. 使用 v0.3.3 binary；
5. 做 integrity/smoke/task-flow 检查。

不要手工修改 `PRAGMA user_version`。

## 8. 重点巡检

- active Attempt 的 `last_renewed` 是否连续；
- `lease_until - last_renewed` 是否接近正常 lease TTL；
- DEADLINE_EXCEEDED 后是否仍有 unreleased Attempt；
- `attempt.stop_escalation` 中 cleanup_confirmed=false；
- Task `seq - event_floor_seq` 是否接近配置上限；
- event_dedup 是否异常快速增长。

event_dedup 的长期 retention 不在 v0.3.4 清理；后续 History/GC 阶段统一处理。

## 9. 边界

v0.3.4 不是 24h 生产认证。真实长任务、真实 Runtime、独立主机和网络故障仍必须完成 Production Baseline #1。
